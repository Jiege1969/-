# 摸清家底找差距实施方案

生成时间：2026-05-05

## 1. 目标

本轮不是继续零散补功能，而是把整套 `D:\杰哥智能化系统` 摸清楚：系统有什么、怎么运行、依赖什么、哪些已达设计要求、哪些只是设计理想、哪些搭建偏离、哪些需要补齐。

最终目标是形成一张可施工、可验收、可复盘的全景图，让后续清理、补文档、补工作流、补自治能力都有依据。

## 2. 已形成的共识

前面讨论已经形成以下共识：

- 四大系统是主骨架：`00总管`、`01智能`、`02扩展`、`03进化`。
- 系统功能本身也是维护对象，不只是维护脚本、日志、备份才需要治理。
- 工作流、日志、验收报告、回滚证据、临时文件、历史草案都属于系统资产，必须分级。
- `F:\系统备份` 是专用备份目录，只用于备份、归档、恢复和回滚证据，不作为临时中转、运行日志或工作流草案目录。
- 股票系统是成熟样板；非股票业务线要按同样标准逐步推进到可验收、可回滚、可接正式口径。
- n8n、Redis、企业微信真实发送、视频真实转换、券商接口和自动交易必须继续受闸门控制。

## 3. 三层扫描框架

### 3.1 骨架

骨架指文件和目录层级：

- 四大系统目录是否清楚。
- 子系统职责是否混放。
- `01配置/02脚本/03数据/04日志/05备份/06临时/07文档` 是否按要求使用。
- README、目录说明、脚本标头、配置说明、文档标题是否补齐。

判断目的：确认系统“长得像不像设计图”。

### 3.2 血脉筋络

血脉筋络指系统实际运行链路：

- 开机计划任务。
- Python 服务。
- Docker 容器。
- 端口监听。
- 企业微信回调。
- n8n 工作流。
- Redis/Ollama/模型路由。
- 日志和回执。

判断目的：确认系统“是否真的能跑、靠什么跑、断在哪里会出问题”。

### 3.3 基因

基因指硬件和主要软件能力：

- Windows 11、CPU、内存、GPU、磁盘。
- Docker、WSL2、Python、Node、n8n、Redis、Ollama。
- 本地模型、WSL2 虚拟磁盘、备份盘。

判断目的：确认系统“能力上限在哪里，哪些设计适合现在做，哪些应后续增强”。

## 4. 三个观察视角

### 4.1 使用者视角

使用者关心：

- 开机后系统是否自动准备好。
- 企业微信机器人能不能回答。
- 股票分析、系统状态、工作秘书、视频助理怎么用。
- 系统慢、不回复、磁盘满时如何判断。
- 系统后台会不会影响办公、股票、视频、游戏。

输出材料：用户操作总览、故障速查卡、机器人使用说明、开机状态说明。

### 4.2 设计者视角

设计者关心：

- 四系统是否各行其责。
- 总管是否仍是唯一准入和调度中心。
- n8n 是否只做编排，不抢总管。
- Redis 是否只是影子增强，不接管正式主链。
- 进化系统是否把经验变成规则。
- 股票系统是否严格保持分析系统。

输出材料：设计纲领对齐审计、四系统达标矩阵、设计与现实差距表。

### 4.3 施工方视角

施工方关心：

- 哪些文件缺说明。
- 哪些脚本缺标头。
- 哪些工作流缺状态。
- 哪些日志能保留、归档、清理。
- 哪些备份在 D 盘，哪些应归到 F 盘。
- 哪些真实动作必须继续关闭。

输出材料：施工补齐清单、工作流台账、日志治理台账、备份索引、清理候选清单。

## 5. 当前已知事实

### 5.1 已达成

- 四大系统目录已成形。
- 股票系统可用，仍为只分析不交易。
- `19300/19302/19310/28100/28679/29134` 健康检查通过。
- Redis 返回 `PONG`。
- Docker 三件套 `Ollama/Redis/n8n` 运行。
- 企业微信当前采用公网 URL 回调，不再采用长连接主用。
- 开机隐藏启动链路已建立。
- 主线脚本标头专项审计 `88/88` 通过。

### 5.2 已知差距

- 工作流相关文件数量大，需要统一台账。
- 日志数量大，需要证据级别和保留期。
- 反向隧道断开后的自动恢复还需补强。
- 进化系统能沉淀规则，但自动反哺总管检查项还不够。
- 非股票业务线多数仍是草案、只读、影子、门禁态。
- 历史 JSON、Markdown、脚本标头仍有存量债务。
- F 盘备份目录已有内容，但缺统一索引和备份口径说明。

## 6. 并行核实任务

本轮采用并行核实，不直接施工。

| 任务 | 核实内容 | 输出 |
|---|---|---|
| A 骨架核实 | 四大系统、子系统目录、README、职责混放、文件层级 | 骨架问题清单 |
| B 血脉核实 | 计划任务、端口、进程、Docker、企业微信回调、服务脚本依赖 | 运行链路图和单点风险 |
| C 基因核实 | 硬件、软件版本、模型、WSL2、磁盘、资源能力 | 能力上限和资源风险 |
| D 证据核实 | 工作流、日志、验收、回滚、F盘备份目录 | 台账/归档/清理优先级 |

## 7. 判断标准

每个核实任务都按以下标准判断：

- 是否符合总纲设计。
- 是否真实运行或只是草案。
- 是否有安全边界。
- 是否有验收证据。
- 是否有回滚证据。
- 是否会影响用户日常使用。
- 是否需要补文档、补脚本、补台账、补自恢复。

## 8. 后续施工队列

并行核实后，按以下优先级施工：

1. 工作流台账：标注正式、禁用、干跑、影子、回滚、废弃。
2. 日志治理：标注运行日志、错误日志、验收证据、历史草案、可清理缓存。
3. F盘备份治理：把 `F:\系统备份` 作为专用备份区，补备份索引、保留期和恢复说明。
4. 反向隧道守护：公网回调断开时自动恢复并记录。
5. 资源调度：按股票时段、办公、视频重任务、日常使用分档。
6. 进化反哺：把故障和成功经验转成总管检查项。
7. 非股票业务线补齐：视频、税收、知识库、内容处理按股票系统交付闭环样板推进。

## 9. 安全边界

本方案阶段只读核实和写报告，不触发 n8n 正式执行，不发送企业微信真实消息，不调用券商接口，不自动交易，不删除业务数据、模型、数据库、日志或备份。
