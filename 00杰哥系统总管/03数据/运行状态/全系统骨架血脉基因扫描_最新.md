# 全系统骨架血脉基因扫描

生成时间：2026-05-05 22:35

## 1. 扫描定位

本次扫描按三层理解整套系统：

- 骨架：文件、目录、四大系统、子系统和层级。
- 血脉筋络：服务、脚本、端口、计划任务、Docker、企业微信回调、n8n工作流、Redis/Ollama依赖。
- 基因：硬件、操作系统、Python/Docker/WSL2/模型/主要软件版本，这些决定系统能力上限和运行风险。

## 9. 代码依赖筋络

扫描 `1201` 个自有 Python 脚本，最常见依赖是 `json/pathlib/datetime/typing/subprocess/sys`，说明当前系统以本地脚本、文件证据、命令调度为主。外部关键依赖包括：

- `fastapi/uvicorn`：本地 HTTP 服务入口。
- `akshare/pandas`：股票数据处理。
- `wecom_aibot_sdk/Crypto`：企业微信智能机器人和加解密。

判断：系统依赖结构偏轻，符合“少引入大平台，先用现有能力搭建”的原则。风险在于 Python 版本偏新、部分外部库少量但关键，需锁定运行环境和依赖清单。

## 12. 严苛结论

这套系统的骨架已经成立，血脉已经能流动，基因条件也足以支撑个人本地 AI 中台。但它不是一个完全自治的成熟智能体系统，而是一个安全优先、股票线成熟、其他业务线受控推进的本地智能中台。

设计没有明显错误，真正的差距在三处：

1. 设计中的“自主运行、自主修复、自主进化”比当前搭建更高级，目前只完成了自检、只读巡检、规则沉淀和部分安全闸门。
2. 工作流、日志、历史验收证据数量大，但治理台账还不够统一。
3. 非股票业务线还没有达到股票系统那种可验收、可回滚、可正式接入口径的成熟程度。

下一步应优先补：

1. 工作流台账：每个 n8n/工作流文件标注正式、禁用、干跑、影子、回滚、废弃状态。
2. 日志治理：按运行日志、验收证据、错误日志、历史草案、可清理缓存分级。
3. 资源调度：按股票时段、办公时段、视频重任务、游戏/日常使用分档。
4. 反向隧道守护：发现公网回调链路断开时自动恢复并记录。
5. 进化反哺：把故障、用户纠偏、成功闭环自动生成总管检查项。
