# 第二轮并行核实汇总

记录时间：2026-05-06 06:10:00 +08:00

核实方式：五线并行，只读核实；未触发 n8n，未发送企业微信真实消息，未调用券商接口，未自动交易，未删除数据。

## 一、总判断

本轮核实的目标不是新增业务功能，而是继续完成“摸清家底找差距”：把系统从“能跑、能用”推进到“知道自己依赖什么、风险在哪里、哪些可以自动恢复、哪些必须人工闸口”。

结论如下：

1. 四系统主骨架已经成型，当前能支撑本地私有化 AI 中台的运行。
2. 股票系统成熟度最高，仍保持 analysis-only，不接自动交易。
3. 企业微信公网回调当前依赖 SSH 反向隧道，服务本机健康，但隧道断线后缺少持续守护，这是当前最明确的 P0 风险。
4. Docker 主线容器已收敛到 3 个，但旧卷、旧镜像仍需归属审计后再清理。
5. D 盘当前空间充足，真正要盯的是 WSL2、Docker、Ollama 三类大体量增长源。
6. Python、Node、Docker/Compose 运行时偏新，正式环境必须补版本锁定和回滚台账。
7. 目录编号冲突不宜立即搬目录，短期应补 README 和目录角色索引，防止系统和人误读职责。

## 二、五线核实结果

### E 公网反向隧道守护

当前 `19302` 本机桥接服务健康，但未发现当前活跃的 `ssh.exe/autossh` 反向隧道进程，也未发现本机到 `43.167.210.211:22` 的已建立 TCP 连接。

历史日志显示，隧道曾在 2026-05-05 晚间可用，2026-05-06 02:09 左右出现 `Connection reset` 后没有被自动拉起。

判断：现状更像“登录时启动一次”，不是“持续守护”。计划任务成功不等于公网通道持续可用。

建议：新增“非业务 probe + 受控 repair”隧道守护。默认只检查本机 `/health`、SSH 进程、PID 一致性、云端 18080 监听和 loopback `/health`；连续失败且本机 `19302` 健康时，才允许只拉起 SSH 隧道，不重启业务服务，不 POST 企业微信业务路径。

### F Docker 卷与镜像归属

当前运行容器只剩：

- `jiege_v3_ollama`
- `jiege_v3_redis`
- `jiege_v3_n8n`

三者均使用 `D:\杰哥智能化系统\01杰哥智能系统\03数据` 下的 bind mount，不使用 Docker 命名卷。

命名卷结论：

- 可作为强清理候选：`qdrant_data`、`redis_data`，实际近空且无容器使用。
- 备份/确认后可清理：`01_n8n-data`、`n8n-data`、`n8n_data`。
- 暂不直接清理：`ollama`、尤其 `ollama_data`，其中可能有当前主线未覆盖的模型 manifest。

镜像结论：

- 必须保留：`ollama/ollama:0.20.5`、`redis:7.2.5-alpine`、`n8nio/n8n:1.123.30`。
- 清理候选：未使用的 `latest`、旧 n8n、旧 Qdrant、旧 Redis、旧本地构建镜像族。

判断：Docker 干扰项已经从“旧容器壳”推进到“旧卷/旧镜像归属审计”阶段；下一步可做清理预案，但还不应直接 prune。

### G D 盘增长与资源监控

当前 D 盘约 781.20GB，总剩余约 394.31GB，短期不紧张。

主要体量：

- `D:\杰哥智能化系统\01杰哥智能系统\03数据\WSL2`：约 189.45GB
- `D:\杰哥智能化系统\01杰哥智能系统\03数据\ollama`：约 133.99GB
- `D:\pagefile.sys`：约 64GB
- Docker `docker_data.vhdx`：约 109.30GB
- Ubuntu `ext4.vhdx`：约 80.03GB

判断：日志和 D 盘本地备份不是当前主要风险；WSL2、Docker、Ollama 才是长期增长主源。

建议阈值：

- D 盘剩余 `<200GB` 或 `<25%` 预警，`<120GB` 或 `<15%` 严重，`<80GB` 或 `<10%` 紧急。
- D 盘单日增长 `>10GB` 预警，`>20GB` 严重，`>40GB` 紧急。
- Ollama `>150GB` 预警，`>180GB` 严重，`>220GB` 紧急。
- Docker VHDX `>130GB` 预警，`>160GB` 严重，`>200GB` 紧急。

### H 版本锁定与依赖风险

已核实运行时存在“版本偏新 + 锁定不完整”的风险：

- Python `3.14.4`
- Node.js `v25.9.0`
- Docker `29.3.1`
- Docker Compose `v5.1.1`
- Ollama 容器锁定 `0.20.5`
- Redis 容器锁定 `7.2.5-alpine`
- n8n 容器锁定 `1.123.30`

判断：容器正式镜像已锁 tag，这是优点；但 Python 依赖只锁了部分直接依赖，股票脚本实际依赖如 `requests`、`beautifulsoup4`、`pypdf`、`pandas`、`akshare`、`baostock` 需要纳入独立 requirements。模型标签中的 `latest` 也要治理。

建议：形成四层升级窗口。

- L4：Docker、WSL、GPU 驱动，单独窗口。
- L3：Python、Node、npm、pip，只在项目本地环境验证。
- L2：n8n、Ollama、Redis，用影子容器或并存端口验证。
- L1：模型文件新旧并存、路由灰度。

### I 目录编号与说明缺口

发现三类说明缺口：

1. `02杰哥扩展系统`：系统级七目录与业务模块同层编号冲突。
2. `03杰哥进化系统`：系统级七目录与能力模块同层编号冲突。
3. `00杰哥系统总管`：`06工具` 与 `06临时` 同层双 06。

另有 `01杰哥智能系统\02脚本\智能体大脑\*接口.py` 容易被误读为业务逻辑进入 01 智能系统，需说明它们只是跨系统只读适配层。

判断：短期不搬目录。现有路径已被大量脚本、报告、台账引用，贸然搬迁会制造新故障。正确做法是补 README、补目录角色索引、补引用关系台账。
