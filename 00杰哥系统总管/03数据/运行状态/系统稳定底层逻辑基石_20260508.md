# 系统稳定底层逻辑基石

- 生成时间：2026-05-08
- 风险等级：W1/R0
- 触发来源：用户指出“这些底层逻辑，就是保证系统稳定的基石”。
- 结论：系统稳定性不应只靠功能是否能跑，而应靠依赖拓扑、闸口判断、边界约束、失败分级和可追溯样本共同保证。

## 一、稳定性的底层判断

系统稳定不是：

- 等够时间就算启动成功。
- 某个端口通了就算业务可用。
- 某次脚本通过就算正式稳定。
- 候选版可用就等于完全交付。

系统稳定应该是：

1. 前置依赖真实就绪。
2. 后置能力按依赖顺序启动或检查。
3. 前置失败时，后置跳过并记录阻断来源。
4. 只读回归通过。
5. 红线保持关闭。
6. 多个真实自然日样本都能复现通过。
7. 每个判断都有文件、日志或回执可追溯。

## 二、核心基石

| 基石 | 含义 |
|:---|:---|
| 依赖拓扑 | 机器资源、Docker、容器、API、业务入口、只读回归、自然日样本必须按顺序成立 |
| 闸口机制 | 前置不通过，后置不硬跑、不误判、不入账 |
| 红线边界 | 外发、n8n、正式库、交易、税务办理、视频发布等高风险动作默认关闭 |
| 只读验证 | 稳定性验证先读状态、读日志、读回执，不直接改业务系统 |
| 失败分级 | P0/P1/P2/P3 不同处理，避免小问题放大，也避免大问题被忽略 |
| 自然日样本 | 稳定不是同一天反复跑出来的，而是跨自然日仍能通过 |
| 可追溯证据 | 每个判断都应能追到脚本、JSON、Markdown、日志或回执 |

## 三、用于发现问题的原理

发现问题不是靠猜，而是按链路定位：

```text
L0 机器资源
  -> L1 Docker 基础
  -> L2 Ollama / Redis / n8n 容器
  -> L3 API / 端口
  -> L4 业务入口
  -> L5 只读总回归
  -> L6 自然日样本
```

如果 L1 失败，L2/L3 不应被误判为自身故障。
如果 L3 失败，L4/L5 不应继续强测。
如果 L5 失败，L6 不得入账。

## 四、对正式稳定版的约束

正式稳定交付版必须满足：

1. 开机自检依赖链路成立。
2. 当日只读总回归通过。
3. 红线扫描通过。
4. 样本来自真实自然日。
5. 至少 3 个不同自然日样本全部通过。
6. 样本齐备后再执行 FS-08 三日达标复核。
