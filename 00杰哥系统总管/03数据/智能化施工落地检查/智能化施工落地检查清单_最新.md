## 二、现实原则

- 硬件是智能体能力的现实边界和设计依据。
- 系统平稳高效是运行能力的现实边界，也是所有智能化能力的前提。
- 不管搭建什么系统，都要把底层逻辑落实到具体文件、脚本、入口、闸口和验收中。
- 已有机制优先复用：模型路由、模型资源池、轻量资源巡检、开机施工准备、日常可用入口、四系统闭环。
- 不把每个好想法都新增为机制；先判断原系统是否已经解决，只补真实缺口。
- 清单分级使用：小修轻量自查，涉及新机制、跨系统、资源、模型或高风险动作时正式跑清单和验证。
- 文稿质检层默认旁路、手动、按需、可关闭；第一阶段不得自动接管正式推送或普通对话链路。
- 学习提炼必须有导航：知道学什么、怎么学、从哪些渠道学，以及什么不能乱学。
- 所有改进候选默认走影子试验、逐步组合、失败隔离机制；系统自主判断和验证，正式切换或不可逆动作才进入用户确认。
- 发现正规、可信、可访问资料时，系统必须先做只读采集、候选抽取、证据映射、质量提示和验收记录，不能把资料未结构化的问题直接转嫁为人工填写任务。
- 自有脚本、维护工具、验收脚本和工作流辅助脚本必须具备标准标头，说明名称、作用、触发方式、依赖、所属系统、输出、安全边界和标识。
- 系统交付按成品口径判断：用户真实使用稳定，不以能跑、可修、有降级链替代完成。
- 股票系统为当前正式业务样板，A股交易保护窗口内不得做影响19300、19302、企业微信入口、公网回调、报告链路、数据源或模型调用的施工。
- 搭建主梁为调度、边界、验收、复用；每次施工都必须说明是否影响这四项。
- 股票系统经验要沉淀为新业务系统可复制搭建能力，复用合格模板，不复制旧问题。
- 旧方案、旧日志、旧端口、旧入口、旧验收口径与最新共识冲突时，搭建者按最新正式链路自行纠偏并记录，不把普通工程判断交给用户。

## 三、施工前必问

1. 这个任务属于哪个系统、哪个业务入口？
2. 是否已有同类机制、脚本、入口、规则或经验卡片？
3. 这是补真实缺口，还是把已有机制重复包装成新复杂度？
4. 是否规则优先，而不是一上来调用模型？
5. 是否需要本地知识检索、向量检索或重排序？
6. 是否需要模型生成？如果需要，是否按需唤醒而非常驻？
7. 是否涉及正式写入、真实发送、n8n触发、券商接口或其他高风险动作？
8. 是否需要人工闸口？
9. 是否需要资源闸口和分时调度？
10. 是否会影响企业微信、股票助手或核心服务平稳可用？
11. 是否会让文稿质检、模型审稿或润色机制进入主链路、常驻运行或自动替换原文？
12. 是否存在正规、可信、可访问资料？如果存在，系统是否已先做只读采集、候选抽取和证据映射，而不是直接要求用户人工填空？
13. 这个改进候选是否已经明确影子环境、单点验证、组合验证、失败隔离和回滚边界？
14. 这次经验是否符合学习提炼导航规则，还是只应写日志不入经验库？
15. 是否有验收、日志、接续和进化候选处理？
16. 是否处于A股交易保护窗口？如果是，是否完全不影响股票系统正式使用？
17. 是否满足成品交付口径，而不是只证明脚本能跑？
18. 是否明确调度、边界、验收、复用四主梁？
19. 是否能沉淀为后续新业务系统的合格模板或规则？
20. 是否存在旧方案、旧日志、旧脚本、旧端口、旧入口或旧验收口径冲突？如存在，是否已按最新正式链路纠偏？

## 四、落地检查项

| 编号 | 名称 | 要求 | 参考文件状态 |
|---|---|---|---|
| A01 | 复用旧机制 | 施工前先查现有设计纲领、配置规则、脚本、工作日志和进化方法，避免重复造轮子；能改已有机制的，不新增同类机制。 | 4/4 |
| A01B | 复杂度克制 | 先判断是缺机制、缺表达还是仅为讨论校准；缺机制才新增脚本或规则，缺表达优先改已有文档，讨论未稳定前不固化。 | 2/2 |
| A02 | 规则优先 | 精确命令、关键词、正则和上下文能解决的，不启用独立路由模型；模糊任务才用小模型兜底。 | 1/1 |
| A03 | 检索增强 | 需要依据时优先检索本地资料；关键词、向量、重排序按需组合，不靠模型记忆编造系统记录。 | 2/2 |
| A04 | 硬件现实边界 | 每个服务和重任务都要说明常驻、按需、定时或手动；重任务要考虑内存、显存、CPU、磁盘IO和核心服务占用。 | 2/2 |
| A05 | 分时调度 | 日常保核心服务，施工窗口跑验收和接续，空闲或夜间跑索引、整理、低风险批处理；资源不足时降级、排队或暂停。 | 2/2 |
| A06 | 人工闸口 | 正式写入、真实发送、n8n触发、券商接口、自动交易、删除迁移等动作必须人工确认，不允许模型直接执行。 | 1/1 |
| A07 | 验收和接续 | 施工后必须有可验证产物、验收脚本或报告，并同步工作日志；施工过程中不反复刷新接续包，只有收工或用户明确要新开对话时才统一固化接续包或施工卡片。 | 2/2 |
| A08 | 进化慎入库 | 日志可以全记录，经验库慎入库；按学习提炼导航判断学什么、怎么学、从哪里学；只有用户打标、失败修复、重复问题、规则变化或可复制机制才进入经验候选。 | 2/2 |
| A09 | 文稿质检旁路 | 文稿质检层第一阶段只能手动触发、旁路审稿、记录结果，不自动替换原文、不自动发送、不常驻模型、不固化正式模板；连续5次用户确认有价值后才评估第二阶段。 | 1/1 |
| A10 | 全系统影子试验与失败隔离 | 任何系统、子系统、模型、工作流、Prompt、脚本、命令、配置、数据源、报告模板或代码改动，都必须具备影子验证、逐步组合、失败隔离和稳定回退意识；粒度越小机制越轻，但原则不变。先单点验证，再按依赖顺序组合验证，再小流量或历史样本验证；任一步失败即隔离失败层，不扩大影响，不影响正式系统。 | 3/3 |
| A11 | 脚本标头规范 | 所有新建或改造的自有脚本必须在文件头部写明八项标头：名称、作用、触发方式、依赖、所属系统、输出、安全边界、标识；第三方库、虚拟环境、缓存、归档副本不纳入主线标头验收。主线脚本缺标头时先补齐，再进入验收和接续。 | 2/2 |
| A12 | 系统先干活 | 当任务存在正规渠道资料、可信本地文件或可只读获取的信息源时，系统必须先完成采集、解析、候选证据抽取、字段映射、质量提示和验收记录；用户只在正式写入、冲突判断、不可逆动作或超出授权范围时做关键确认。不得把“资料未结构化核验入账”误判为“用户必须从零人工填写”。 | 3/3 |
| A13 | 成品交付口径 | 交付必须按用户真实使用结果判断；核心功能在约定范围内必须稳定可用。自动巡检、恢复、降级和回滚只能作为成熟产品保障，不能作为交付缺陷的理由。 | 2/2 |
| A14 | 交易保护与施工避让 | A股交易日09:30-11:30、13:00-15:00为最高保护窗口，建议09:00-15:30作为施工保护窗口。保护窗口内只做只读检查、日志查看、文档整理和不影响正式入口的准备动作。 | 2/2 |
| A15 | 调度边界验收复用四主梁 | 每个新功能、新系统、新脚本、新模板和新工作流必须说明其调度时机、能力边界、验收口径和可复用价值；无法说明时不得进入主线施工。 | 1/1 |
| A16 | 新业务系统可复制搭建 | 后续新业务系统必须继承合格模板：目录、入口、日志、验收、状态面板、边界、接续、备份和经验沉淀；不得从空白开始，也不得复制股票系统踩坑历史。 | 1/1 |
| A17 | 旧口径冲突自动纠偏 | 旧方案、旧日志、旧脚本、旧端口、旧入口、旧验收口径与最新共识或正式可用链路冲突时，搭建者应按最新正式链路自行纠偏、记录日志并运行相关验收；只有高风险和超授权事项才询问用户。 | 2/2 |

## 七、使用方式

- 小修小补：按本清单做轻量自查即可，不必机械新增文件。
- 涉及新机制、跨系统、模型、资源、闸口或高风险动作：正式跑本清单和验证脚本。
- 能复用旧机制的，不重新造轮子。
- 能修改已有文件的，不新建同类文件；能写日志的，不升级成新机制。
- 需要重任务时，先判断是否适合当前时间段和资源状态。
- 高风险动作只做到预览和闸口，必须人工确认后再继续。
