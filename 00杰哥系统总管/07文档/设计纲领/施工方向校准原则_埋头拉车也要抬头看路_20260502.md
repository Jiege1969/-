# 施工方向校准原则：埋头拉车，也要抬头看路

生成日期：2026-05-02

## 一、为什么要有这条原则

杰哥智能化系统是在真实问题中搭建的。真实问题会不断出现，解决问题必须脚踏实地，但如果只盯着眼前故障，就容易跑偏：

- 为了修一个点，堆出一堆临时脚本。
- 为了一个入口，破坏主流程。
- 为了一个具体需求，忘记四大系统分工。
- 为了快速可用，忘记验收、接续和经验沉淀。

因此，后续施工必须同时满足两件事：

```text
埋头拉车：具体问题必须解决，真实功能必须可用。
抬头看路：每次修改都要回到总目标、总原则、总边界和闭环路线。
```

## 二、总方向

当前总方向不变：

1. 股票分析系统作为真实业务试验场，继续稳定和优化。
2. 总管、智能、扩展、进化形成四系统小闭环。
3. 每次真实问题暴露后，尽量转化为规则、脚本、验收和经验。
4. 股票系统闭环稳定后，再推广到其他业务系统。

核心路线：

```text
真实业务试验场 -> 问题暴露 -> 规则修正 -> 脚本固化 -> 验收护栏 -> 经验沉淀 -> 总管调度下一轮
```

## 二点五、努力与方向一致性

埋头拉车和抬头看路不是二选一。

埋头拉车，要求系统脚踏实地、一步一个脚印，把眼前真实问题解决掉；抬头看路，要求系统高瞻远瞩，看清目标、道路和边界，避免陷入方向性错误。

最危险的状态不是停下来，而是在错误方向上越来越努力：

```text
方向错误 -> 执行越勤奋 -> 产物越多 -> 偏差越大 -> 修复成本越高
```

因此，后续施工必须同时确认：

- 当前动作是否真的解决用户可感知问题。
- 当前动作是否仍服务系统总目标。
- 当前动作是否符合本末终始和先后次序。
- 当前动作是否会把局部补丁包装成主线方向。
- 当前动作是否会让系统进入“越努力越错误”的循环。

如果发现方向可能错误，必须先停在方向校准，不继续用执行速度掩盖路线问题。

## 三、每次施工前的方向检查

每次开始施工前，至少确认：

1. 当前用户问题属于哪个层面：
   - 具体功能故障。
   - 前台体验优化。
   - 数据可信度补强。
   - 证据核验链路。
   - 总管/接续/验收治理。
   - 进化系统经验沉淀。
2. 是否影响股票系统主流程。
3. 是否影响四大系统分工。
4. 是否触碰安全边界。
5. 是否需要同步接续包、日志、设计纲领或进化经验。

## 四、每次施工后的方向复盘

每次完成后，至少回答：

1. 解决了什么真实问题。
2. 是否保持了总目标方向。
3. 是否新增了临时口子或重复入口。
4. 是否需要进入验收护栏。
5. 是否需要沉淀为经验。
6. 是否已经同步到接续文件。

## 五、禁止跑偏

以下行为要避免：

- 只修眼前，不更新接续文件。
- 只写文档，不落到脚本或验收。
- 只加脚本，不考虑是否重复。
- 只追求自动化，不守安全边界。
- 只看股票系统，不看它对总管、智能、进化的牵引作用。
- 一遇到新想法就扩大到全系统，跳过股票系统试验场。
- 只因为已经投入很多，就继续沿错误方向追加施工。
- 用产物数量、脚本数量、回执数量掩盖方向偏差。
- 把局部应急补丁误升为全系统长期路线。

## 六、允许的务实做法

允许先小步做：

- 先修一只股票报告，再推广到报告模板。
- 先修一个企微入口，再固化为前台回归验收。
- 先修一次数据口径，再形成数据口径检查。
- 先在股票系统内部沉淀方法，再迁移到其他系统。

这就是“以点带面”，不是“头痛医头”。

## 七、归口

本原则归口到：

- 00总管：负责方向、边界、接续和验收。
- 03进化系统：负责把跑偏风险、修复经验和方法沉淀成可复用能力。

后续所有较大施工，都应以本原则作为方向校准依据。
