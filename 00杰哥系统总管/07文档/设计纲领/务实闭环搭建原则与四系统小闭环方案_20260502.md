# 务实闭环搭建原则与四系统小闭环方案

生成日期：2026-05-02

## 一、核心判断

杰哥智能化系统的搭建，不应停留在“设计得很完整”，而要通过真实业务持续检验。

当前最合适的试验场是股票分析系统。它已经具备真实数据、真实查询、真实企业微信入口、真实报告、真实问题暴露和真实验收链路，能够检验系统的家底：模型能力、脚本能力、数据治理能力、服务稳定性、前台交互能力、接续能力和经验沉淀能力。

本原则可以概括为：

```text
真实业务试验场 -> 问题暴露 -> 规则修正 -> 脚本固化 -> 验收护栏 -> 经验沉淀 -> 总管调度下一轮
```

这就是从设计到落地、从理论到实际、用实践检验真理的路线。

## 二、以点带面的台阶

系统不追求一次性大而全，而是按台阶推进：

1. 一只股票实验成功。
2. 一个股票池运行成功。
3. 股票分析系统完整成功。
4. 扩展系统中的真实业务闭环成功。
5. 总管、智能、扩展、进化四系统形成小闭环。
6. 在小闭环稳定后，再推广到税收、知识库、本职工作、内容办公等系统。

每个台阶都必须有可用结果、问题记录、修复动作、验收结论和经验沉淀。没有验收和沉淀的功能，不算真正完成。

## 三、四系统小闭环

### 00杰哥系统总管

职责：定边界、定计划、看验收、管接续。

在小闭环中，总管负责回答：

- 当前哪个系统可用。
- 哪些动作禁止。
- 哪些验收通过。
- 下一步施工顺序是什么。
- 新对话或另一个AI如何接手。

### 01杰哥智能系统

职责：提供模型、服务、运行时、企业微信入口、n8n和工具底座。

在小闭环中，智能系统负责回答：

- 本地模型是否可用。
- 服务是否正常。
- 企业微信入口是否连通。
- Docker、Ollama、Redis、n8n等底座是否稳定。

### 02杰哥扩展系统

职责：承载真实业务。当前第一个重点样板是股票分析系统。

在小闭环中，扩展系统负责输出：

- 可查询。
- 可推荐。
- 可出报告。
- 可推送或生成推送草案。
- 可复盘。
- 可验收。

### 03杰哥进化系统

职责：把问题和成功经验变成能力。

在小闭环中，进化系统负责沉淀：

- 问题根因。
- 修复经验。
- 可复用规则。
- 验收护栏。
- 方法候选。
- 后续优化建议。

## 四、股票系统作为第一试验场

股票系统当前已经暴露并推动了多类真实问题：

- 企业微信点击详情不识别日报股票。
- 手机和电脑企业微信显示机制不同。
- 前台报告不应堆后台分析过程。
- 模型可能自行换算成交额单位，出现“万亿元”等异常。
- 推荐等级、系统评分、星级和单股评分需要区分。
- 新对话接手必须依赖接续包和快速状态检查。

这些问题的价值在于：它们不是纸面设计能发现的，而是真实使用暴露出来的。每修复一个问题，都要尽量转成规则、脚本、验收和经验卡片。

## 五、施工原则

1. 真实使用优先：优先修复用户在真实使用中遇到的问题。
2. 小步闭环优先：每次只把一个问题从发现推进到验收，不散开成大工程。
3. 前后台分离：后台可以复杂，前台必须结论化、人话化、可用化。
4. 问题能力化：重要问题不能只写日志，必须进入脚本、规则、验收或进化系统。
5. 护栏优先于扩张：发现前台退化、数据口径异常、服务断链等问题，先建护栏，再加功能。
6. 不自动越权：真实发送、n8n自动触发、正式写库、删除、重启正式服务、券商接口、自动交易仍需闸口。
7. 从样板推广：股票系统跑稳后，再把方法迁移到其他扩展系统，不提前大面积推广。

## 六、当前最小可行闭环

当前最小闭环不是另起炉灶，而是在已有股票系统上补齐四系统协作：

```text
总管读取验收和计划
-> 智能系统保障模型/服务/企微入口
-> 扩展系统运行股票查询、推荐、报告和回归验收
-> 进化系统记录问题、经验和规则候选
-> 总管更新接续包和下一轮计划
```

当前股票系统已具备：

- 完全交付最终验收 5/5。
- C+++ 日常可用总验收 16/16。
- 企微前台交互回归 20/20。
- 报告数据口径检查通过。
- 日常一键运行失败数 0。

因此，下一步不是重新定义大系统，而是把股票系统暴露出的经验持续写入总管和进化系统。

## 七、下一步计划

1. 以股票系统为试验场，继续补公司经营、催化剂事件、风险失效条件和行业政策环境卡片。
2. 每次真实问题修复后，同步更新：
   - 工作日志。
   - 接续包。
   - 施工卡片。
   - 必要的验收脚本。
   - 进化系统经验卡片。
3. 建立“四系统小闭环状态摘要”，用来回答：
   - 总管有没有最新计划。
   - 智能底座是否正常。
   - 扩展业务是否可用。
   - 进化系统是否沉淀了本轮经验。
4. 小闭环稳定后，再把股票系统方法推广到其他业务系统。

## 八、验收口径

一项优化是否真正完成，不看是否写了代码，而看是否同时满足：

- 用户真实问题被解决。
- 输出结果可读、可用、可复验。
- 相关规则被记录。
- 必要脚本或验收护栏已更新。
- 接续文件已同步。
- 没有越过安全边界。

符合这些条件，才算从“施工动作”上升为“系统能力”。

## 九、从股票样板到自动复制搭建新系统

股票系统不是终点，而是第一个成品样板。

四系统小闭环的更高目标，是让系统掌握“如何搭建一个业务系统”的方法。后续税务、文稿、视频、资料整理等扩展系统，不应从空白开始，也不应重复股票系统踩过的坑。

新业务系统复制搭建时，必须继承以下合格能力：

- 业务目标和用户使用场景定义。
- 入口、数据区、脚本区、日志区、报告区、验收区和状态面板。
- 企业微信或本地入口的前台输出标准。
- 脚本标头、安全边界、触发方式、依赖和输出说明。
- 总管登记、开工快检、日常巡检、接续边界和备份策略。
- 影子试验、逐步组合、失败隔离和回滚口径。
- 文稿或报告的手机端可读性、结论先行和证据链要求。
- 进化系统的经验候选、引用效果和降级清理机制。

复用原则：

- 复用合格模板，不复制混乱历史。
- 复用经过验收的规则，不复制临时补丁。
- 复用用户确认后的体验标准，不复制后台技术口径。
- 复用股票系统暴露并已修复的问题教训，防止新系统重犯。

## 十、交易保护与施工避让

股票系统当前属于正式使用中的生产业务样板。任何四系统闭环施工，都不得影响股票系统正常使用，尤其是交易日白天。

执行口径：

- A股交易日 `09:30-11:30`、`13:00-15:00` 为最高保护窗口。
- 建议 `09:00-15:30` 作为交易日股票系统施工保护窗口。
- 节假日、周末、非交易日除外，但仍需遵守影子试验、回滚、验收和安全边界。
- 保护窗口内只允许只读检查、日志查看、文档整理、方案讨论、非运行链路准备和不影响正式入口的轻量动作。
- 会影响 19300、19302、公网回调、企业微信入口、报告生成、数据源、模型调用或正式图文详情的动作，必须放到收市后、夜间、影子环境或用户明确授权窗口。

白天发现问题时，原则是先保服务、后根因施工：

- 不影响使用的问题，记录后收市处理。
- 影响使用的问题，优先恢复到上一个稳定状态，不做现场大重构。
- 需要高风险动作的问题，先保持可用，再在合适窗口按影子试验和验收链路处理。

## 十一、搭建者职责与旧口径冲突处理

讨论期可以充分推敲；一旦方案确认进入施工，搭建者负责交付结果。

以下事项属于搭建者职责，不应反复询问用户：

- 旧入口、旧端口、旧脚本、旧验收口径与最新正式链路冲突。
- 脚本标头缺失、日志未同步、状态面板读取旧最新文件。
- 已确认前台体验标准未固化到模板或验收。
- 旧日志与最新共识冲突，需要按最新共识纠偏。

处理规则：

- 最新确认的总目标、正式可用链路和最新验收结果优先于旧日志。
- 发现冲突后先审计，属于既定目标范围内的直接纠正。
- 纠正后必须写工作日志并跑相关验收。
- 只有涉及删除迁移、覆盖正式数据、改变用户使用习惯、外部账号安全、不可逆动作或超出授权范围时才询问用户。
