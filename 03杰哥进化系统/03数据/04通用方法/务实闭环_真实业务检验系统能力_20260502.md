# 务实闭环：用真实业务检验系统能力

生成日期：2026-05-02

## 来源

股票分析系统真实搭建和使用过程中形成的阶段性方法。代表性问题包括：企业微信点击详情识别断层、前台报告堆后台过程、成交额单位异常、接续包同步和回归验收固化。

## 核心经验

系统能力不能只靠设计说明证明，必须在真实业务里检验。

有效路线是：

```text
真实业务试验场 -> 问题暴露 -> 根因定位 -> 规则修正 -> 脚本固化 -> 验收护栏 -> 经验沉淀
```

## 方法解释

1. 先选一个真实业务样板，不同时铺开多个业务。
2. 让真实用户问题暴露系统短板。
3. 每次修复都要尽量转成可复用规则，而不是只修一处。
4. 重要经验必须进入脚本、验收、接续包或进化系统。
5. 当一个业务样板稳定后，再迁移方法到其他业务。

## 当前样板

股票分析系统是第一试验场：

- 完全交付最终验收：5/5。
- C+++ 日常可用总验收：16/16。
- 企业微信前台交互回归：20/20。
- 报告数据口径检查：通过。

## 可复用场景

该方法后续可迁移到：

- 税收业务系统。
- 知识库系统。
- 本职工作系统。
- 内容办公系统。
- 企业微信统一助手。

但迁移前提是：股票系统闭环稳定，并且相关方法已形成明确规则和验收口径。

## 禁止误用

- 不把“闭环”理解成一次性大而全搭建。
- 不把文档数量当作进度。
- 不把脚本堆叠当作智能。
- 不把未经核验的经验自动写入正式规则。
- 不越过真实发送、正式写库、自动交易等安全边界。
