# 股票样本复用施工原则

生成时间：2026-05-06 06:40:00 +08:00

## 一、定位

股票分析系统是当前最完整的样本工程。后续搭建知识库、税收、内容、视频、工作秘书等系统时，不能只复用它的功能成果，也必须复用它暴露出来的债务教训。

股票分析系统在后续搭建中只作为母样本：复用成功结构、验收链路、安全边界和证据链，不继承旧债、旧流水、旧入口、旧提示词候选和股票业务专用语义。

股票系统作为底基和样本，是本系统能快速成型的重要原因；同时，它也是目录、日志、工作流、守护、台账等债务被带入其他环节的原因之一。因此后续复用必须采用“样本提纯”方式：吸收有益基因，剥离无益债务，禁止整包照抄。

本原则分两层：

1. 当前纠偏：把股票系统建设中已经暴露的问题补规则、补台账、补闸口。
2. 未来戒律：把这些问题转成新系统开工前必须执行的施工原则。

## 二、当前需要纠偏的债

| 债务 | 当前纠偏 |
|---|---|
| 目录编号和职责口径不够早锁定 | 先补 README、角色索引、目录编号总图；不为美化编号搬正式目录 |
| 日志散落、级别和保留期不足 | 建立四级日志、事件ID、保留期和日志台账 |
| 上线只重功能脚本，守护和验收后补 | 建立上线八件套：功能、探针、日志、验收、回滚、人工闸口、安全边界、台账 |
| n8n 工作流和自动化资产缺少统一台账 | 新增工作流必须登记用途、状态、依赖、禁用/启用口径 |
| 公网隧道、探针等运维能力起初滞后 | 新系统上线当天必须同步守护、探针和异常记录 |
| 旧路径、旧容器、旧卷容易被误读 | 历史资产必须标注禁用、历史、候选、正式四类状态 |

## 三、后续搭建工程施工原则

### 0. 先提纯样本，再复用样本

任何系统借鉴股票系统前，必须先拆成三张清单：

- 成功基因：可以复制。
- 债务教训：必须纠正后再复制。
- 禁止复发项：不得带入新系统。

不得把“股票系统已经跑通”理解成“股票系统所有做法都可复用”。

## 四、股票样本提纯矩阵

| 股票系统经验 | 性质 | 复用方式 | 禁止事项 |
|---|---|---|---|
| 分层池、分阶段推进、从 L8 到 L5 逐步收敛 | 成功基因 | 税收、知识库、内容等系统也采用分层交付，不一次堆全功能 | 禁止一上来做全链路自动化 |
| analysis-only、安全边界、人工确认 | 成功基因 | 所有业务系统先只读分析、报告、建议，不直接外部执行 | 禁止把分析输出变成自动动作 |
| 质量面板、历史记录、验收脚本 | 成功基因 | 每个系统必须有状态面板、历史摘要、验收入口 | 禁止只有功能脚本无质量闭环 |
| 企业微信、n8n、Docker、模型联动 | 成功基因但高风险 | 先 shadow/dry-run，台账齐全后再进灰度 | 禁止未经门禁直接启用真实发送或 webhook |
| 目录和编号早期未锁死 | 债务教训 | 新系统开工前先定目录编号、职责和 README | 禁止边做边长出旧路径 |
| 日志散、保留期不足 | 债务教训 | 新脚本必须声明日志级别、事件 ID、保留期 | 禁止日志随脚本散落 |
| n8n 工作流重复、台账滞后 | 债务教训 | 工作流先登记业务归属、风险、回滚、禁用状态 | 禁止无台账导入 n8n |
| 守护和探针后补 | 债务教训 | 上线当天同步探针、日志、验收、回滚 | 禁止“能跑就算上线” |
| 旧路径、旧任务、旧配置残留 | 禁止复发项 | 证据充分无依赖时同轮收口 | 禁止留档观察以后处理 |
| 股票业务特定指标、行情结构、研究口径 | 业务专用 | 只能作为模式参考，不可直接搬给税收/办公/内容系统 | 禁止把股票业务模型当通用业务模型 |

## 五、各系统落地方式

### 税收系统

吸收：

- 分层资料池、证据链、报告生成、人工确认。

纠正：

- 不复制股票行情/交易语义。
- 不引入自动申报、自动提交、外部系统写入。
- 税收知识库必须先有来源、版本、适用地区和有效期。

### 总管系统

吸收：

- 状态面板、验收收口、事件链、质量历史。

纠正：

- 总管只做协调、探针、台账、闸门，不下沉成具体业务系统。
- 不复制股票系统里业务逻辑和总管职责混杂的早期做法。

### 进化系统

吸收：

- 复盘、经验卡、规则沉淀、反退化检查。

纠正：

- 不把所有过程材料都堆成永久待办。
- 规则必须能阻断施工，而不是只做文档陈列。

### 智能系统

吸收：

- 模型路由、提示词模板、只读问答、质量评估。

纠正：

- 提示词必须版本化。
- 模型和依赖必须有清单。
- 不让模型直接越过人工闸口触发外部动作。

### 其他扩展系统

吸收：

- 股票系统的“先样本、再灰度、再正式”的施工节奏。

纠正：

- 每个业务系统必须先声明自己的业务边界、数据资产和禁止动作。
- 不能只复制股票系统的目录形状，而不复制治理规则。

## 六、后续搭建工程施工原则

### 1. 先定边界，再写功能

新系统开工前必须写清：

- 归属系统。
- 业务线名称。
- 数据目录。
- 日志目录。
- 入口方式。
- 禁止动作。
- 人工闸口。

没有边界的功能，不进入施工队列。

### 2. 先建台账，再堆资产

任何新增资产都必须能被台账找到：

- 脚本台账。
- n8n 工作流台账。
- Docker 卷/镜像台账。
- 计划任务台账。
- 模型和依赖版本台账。
- 日志与证据台账。

没有台账的资产，默认不得进入正式态。

### 3. 先只读，再灰度，最后正式

新业务必须按四段推进：

1. 草案。
2. 只读影子。
3. 人工许可灰度。
4. 正式执行。

跳过只读影子和人工许可的外部动作，一律阻断。

### 4. 上线必须带守护

上线不是“脚本能跑”。上线至少包括：

- 功能脚本。
- 健康检查或探针。
- 日志接入。
- 验收标准。
- 回滚方式。
- 异常事件记录。

凡是对可用性有影响的入口，必须同步有守护或只读监测。

### 5. 样本成功不能掩盖样本债务

股票系统可以作为可交付样本，但不能无脑复制它的早期混乱：

- 不复制散日志。
- 不复制无台账工作流。
- 不复制旧路径口径。
- 不复制先上线后补守护。
- 不复制没有保留期的临时输出。

## 七、新系统开工检查

后续任何系统搭建前，必须回答：

1. 它借鉴了股票系统哪些成功模板。
2. 它规避了股票系统哪些技术债。
3. 它有哪些股票业务专用内容不得复制。
4. 它的目录编号是否已登记。
5. 它的日志级别和保留期是否已声明。
6. 它的上线清单是否完整。
7. 它是否有只读探针或 dry-run。
8. 它是否有人工闸口和回滚方式。
9. 它是否满足清债不添新债原则。

## 八、安全边界

本原则只作为工程施工约束；不触发 n8n，不发送企业微信，不调用券商接口，不自动交易，不删除或移动正式数据。
