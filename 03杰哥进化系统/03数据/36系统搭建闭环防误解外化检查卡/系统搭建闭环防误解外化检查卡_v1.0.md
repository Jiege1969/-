# 系统搭建闭环防误解外化检查卡 v1.0

创建日期：2026-05-07  
所属系统：03杰哥进化系统  
资产身份：跨系统影子检查模板

## 定位

这张卡用于把“能做就闭环、不能把规则当借口欠债”的判断外化出来。以后任何业务系统施工时，不能只说“已建schema、已写草案、后续接入”，必须回答用户最终能感知什么、缺口是什么性质、能不能先做影子闭环、是否涉及W3确认。

## 必答六问

1. 这个动作解决哪个用户可感知问题？
2. 这是能力外缺口，还是已有能力但未闭环？
3. 能否先做影子闭环验证，而不是只做草案？
4. 是否涉及W3资产？
5. 是否存在P0旧债未闭环？
6. 前台输出是否体现结论，后台是否保留证据链？

## 判定规则

- 如果只能写出schema、字段、脚本或草案，不能宣称能力完成。
- 如果已有字段、脚本、数据源、人工材料可以补齐，应按“未闭环”处理，不得长期写成“待接入”。
- 如果不触发正式入口、不外发、不自动执行，优先做影子样例，让用户先看到结果形态。
- 如果涉及正式配置、正式脚本、工作流契约、生产入口、企业微信真实发送、n8n、服务、外发、券商接口、自动交易、自动申报，必须暂停确认。
- 如果P0旧债直接影响用户体验或核心报告质量，必须优先收束，不得横向扩展低风险草案。

## 外化输出格式

```json
{
  "user_visible_change": "",
  "gap_classification": "ability_gap / unclosed_loop / external_dependency",
  "why_not_done_yet": "",
  "minimum_closure_path": [],
  "shadow_output_path": "",
  "formalization_blockers": [],
  "pause_confirmation_needed": false,
  "next_action": ""
}
```

## 本次案例固化

股票财报问题不是单纯“没有数据源”，而是已有经营快照字段、补财报脚本和人工核验材料没有进入单股报告与企业微信短答闭环。正确动作不是继续写“财报待接入”，而是先做财报结构化影子闭环和用户可感知短答样例；若要改正式入口，再按W3暂停确认。

这个逻辑可迁移给税务、政策证据库和后续系统，但只能迁移“闭环判断方法”，不能迁移股票指标、行情、价位、交易话术，也不能让股票系统宣布自己是全系统标准。
