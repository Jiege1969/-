# PowerShell中文编码系统治理经验卡片

生成时间：2026-04-29

## 一、问题现象

股票系统交付运行入口、状态检查脚本在 Windows PowerShell 5 中执行时，中文脚本名、中文路径、中文属性名被错误解析为乱码。

典型表现：

- `-File` 参数里的中文脚本名被解析成乱码路径，提示文件不存在。
- 脚本内部访问中文属性名时出现语法错误。
- 单个脚本用 UTF-8 Base64 绕过后，其他脚本仍可能继续出现同类问题。

## 二、根因判断

根因不是某一个脚本写错，而是编码机制问题：

- Windows PowerShell 5 对无 BOM 的 UTF-8 脚本会按系统 ANSI 编码读取。
- 新系统大量使用中文目录和中文文件名，放大了该问题。
- 只在单个脚本里绕过中文路径，属于局部补丁，不能消除同类风险。

## 三、处理过程

本次先用局部 Base64 方法让关键交付链路跑通，随后回到根因层面做系统治理：

1. 识别乱码发生位置：脚本名、路径、属性名。
2. 判断根因：PowerShell 5 读取无 BOM UTF-8 的兼容性问题。
3. 界定范围：只处理 `D:\杰哥智能化系统` 内自有 `.ps1`，排除 `.venv` 第三方目录。
4. 系统修复：统一转换为 UTF-8 BOM。
5. 固化验收：新增 `验证PowerShell脚本UTF8BOM编码.ps1`，后续可重复检查。
6. 回归验证：股票交付运行入口、公网回调状态、股票总验收重新通过。

## 四、验证结果

- 自有 PowerShell 脚本：26/26 通过 UTF-8 BOM 验收。
- 股票系统交付运行入口：可重复执行。
- 公网回调状态：`ready`。
- 股票系统交付使用版总验收：11/11 通过。

## 五、可复用方法

遇到类似问题时，不按“哪个脚本报错修哪个脚本”的方式处理，而按下面顺序处理：

1. 先判断这是个体错误还是机制错误。
2. 如果同类风险会在多个脚本中复现，必须做系统级治理。
3. 修复对象要有边界，避免误动第三方目录或旧系统。
4. 修复后必须增加验收脚本，使问题以后能自动发现。
5. 最后把验收接入运行入口或总体验收，而不是只留下口头经验。

## 六、底层原则

- 谨慎不是墨守成规，谨慎是找到边界后果断治理。
- 不越矩的目的不是不行动，而是不误伤、不扩大风险。
- 局部补丁只能救急，机制问题必须系统解决。
- 经验不能只写成文字，必须转化为脚本、规则、验收和运行闭环。
- 简单适用优先：本次用 UTF-8 BOM 解决 PowerShell 5 兼容问题，比到处写 Base64 路径更稳定。

## 七、适用范围

- Windows PowerShell 5 环境。
- 使用中文目录、中文脚本名、中文属性名的自动化系统。
- 开机自检、登录自启动、运维脚本、交付运行入口。
- 新建 `.ps1` 脚本的编码规范。

## 八、不适用边界

- PowerShell 7 可以更好支持 UTF-8，但本机仍需兼容 Windows PowerShell 5。
- 第三方目录、虚拟环境、外部依赖包不应批量改写编码。
- 编码治理不能替代业务逻辑验收，修复编码后仍需跑业务验收。
