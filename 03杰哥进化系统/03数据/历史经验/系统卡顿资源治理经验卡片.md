# 系统卡顿资源治理经验卡片

生成时间：2026-04-29

## 一、现象

用户反馈本机明显卡顿。检查发现 CPU 并未持续满载，但可用内存一度接近 0，提交内存接近上限，系统发生明显分页和内存压缩。

## 二、根因

1. 旧系统容器栈重复运行，占用额外资源，其中旧 `jiege_ollama` 曾单独占用约 6.6GB 内存。
2. `生成双系统Ollama治理审计.ps1` 存在失控长驻风险，曾出现单个 PowerShell 进程私有内存约 159GB 的异常状态。
3. 股票助手启动脚本使用 WindowsApps `python.exe` 包装器，进程列表出现包装进程和真实 Python 进程双层结构，容易误判为孤儿进程。

## 三、处理办法

- 停止旧系统重复容器栈，只保留新系统核心容器和必要 Ollama。
- 停止失控 PowerShell 审计进程。
- 将 `生成双系统Ollama治理审计.ps1` 改为默认暂停，必须显式 `-ForceRun` 才执行深度审计。
- 优化股票助手和企业微信桥接启动脚本，优先解析真实 Python 解释器，减少 WindowsApps 包装进程。
- 恢复股票助手、企业微信桥接和公网 SSH 回调隧道。

## 四、验收结果

- 可用内存恢复到约 44GB。
- CPU 回落到约 15%。
- 股票公网回调状态：ready。
- 股票系统交付使用版总验收：11/11 通过。
- Docker 运行容器收敛为新系统核心容器和必要 Ollama。

## 五、可迁移逻辑

系统卡顿不能只看 CPU。必须同时看：

1. 可用内存。
2. 提交内存和提交上限。
3. 单进程私有内存。
4. 重复容器和重复基础服务。
5. 启动脚本是否产生包装进程、孤儿进程或长驻进程。

## 六、安全边界

本次只停止重复旧容器和失控审计进程，不删除文件、不清理数据、不写旧系统、不真实发送企业微信、不触发交易接口。
