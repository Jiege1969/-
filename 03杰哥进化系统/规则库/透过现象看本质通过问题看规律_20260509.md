# 透过现象看本质，通过问题看规律

> 生效日期：2026-05-09
> 所属系统：03杰哥进化系统 / 规则库
> 定位：宪法级认知工作法，用于问题处理、归因复核、规则升级和能力下沉。

## 一、核心原则

系统遇到问题时，不能只停留在表面现象，也不能只为通过当次检查而修补。必须通过现象追问本质，通过具体问题提炼规律，再把规律转化为规则、检查器、模板、面板、接续包或业务子系统能力。

```text
现象
-> 本质
-> 规律
-> 机制
-> 能力
```

## 二、四层判断

### 1. 现象层

记录看得见的事实：
- 报错是什么。
- 哪个检查失败。
- 哪个目录复发。
- 哪个端口异常。
- 哪条规则冲突。
- 哪个用户体验不对。

### 2. 本质层

追问真实原因：
- 是路径旧债，还是服务双栈。
- 是规则层级倒置，还是样本证据不足。
- 是红线边界不清，还是下位条件压过上位目标。
- 是脚本缺陷，还是设计假设错误。
- 是一次偶发，还是结构性问题。

### 3. 规律层

提炼可复用规律：
- 下位规则不能压过上位目标。
- 条件不是目的，条件服务证明目标。
- 不能删症状不治源头。
- 单项指标不能替代综合裁决。
- 稳定不是时间给的，是系统事实证明的。
- 问题修复必须保留原始失败事实、修复动作和复验证据。

### 4. 机制层

把规律落成系统机制：
- 写入规则库。
- 形成只读检查器。
- 更新面板和接续包。
- 下沉到四大系统和业务子系统模板。
- 后续遇到同类问题时自动调用该规律。

## 三、问题处理最低回执

每个重要问题至少输出：

```text
现象：发生了什么。
本质：根因是什么。
规律：暴露了哪类共性方法论。
机制：本次如何沉淀到系统。
复验：如何证明问题已解决。
边界：是否触碰红线。
```

## 四、禁止事项

- 不得只修当次报错，不分析根因。
- 不得只写现象，不提炼规律。
- 不得把规律停留在对话中，不纳入系统。
- 不得为了加快进度跳过复验。
- 不得把经验当作绝对真理，仍需实践检验和持续修正。

## 五、当前案例吸收

2026-05-09 冷启动复验中，`D:\01杰哥智能系统` 复发的现象，暴露出的本质是 Ubuntu 本地 Docker 旧底座双栈自启，进一步提炼出规律：不能删症状不治源头；不能让下位规则压过上位目标；稳定不是日期给的，而是系统事实证明的。

该规律已沉淀为规则层级、稳定版上位目标、自然日样本可信性和本认知工作法。
