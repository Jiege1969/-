# 旧系统可复用资产吸收与反适配规则

> 版本：v1.0  
> 生效日期：2026-05-08  
> 所属系统：03杰哥进化系统 / 规则库  
> 依据来源：`F:\系统备份\20260425全量备份\系统文件备份\老系统可复用资产_20260426`  
> 定位：从老系统资产中吸收已验证的思想、结构、故障经验和运行机制，同时防止旧脚本、旧端口、旧密钥、旧工作流和旧口径原样污染新系统

## 一、总原则

老系统资产是矿，不是成品。

可复用的是经过验证的机制、经验、边界和故障处理方法；不可直接复用的是旧目录、旧端口、旧密钥、旧工作流、旧服务名、旧数据结构和未经验证的自动化动作。

吸收老系统资产必须执行：

```text
只读识别 -> 价值分层 -> 反适配检查 -> 影子验证 -> 新系统规则化 -> 接续记录
```

## 二、资产分层

| 层级 | 可吸收内容 | 处理方式 |
|:---|:---|:---|
| A层：原则与方法 | 搭建总纲、系统纲领、施工规程、运维手册中的稳定、边界、根因、闭环思想 | 可提炼进规则库 |
| B层：经验与ADR | 模型丢失、幽灵服务、端口冲突、服务名漂移、稳定模式等已验证案例 | 可转为故障卡、验收项、排障规则 |
| C层：结构与模板 | 七目录结构、脚本标头、服务登记、端口分配、收工固化 | 可反适配到新系统模板 |
| D层：代码与工作流 | 感知、记忆、决策、行动模块，n8n工作流，企业微信接入脚本 | 只能影子分析，不直接替换新系统 |
| E层：敏感与旧状态 | 密钥、数据库备份、n8n内部库、旧端口、旧服务配置 | 只登记存在与风险，不读取扩散，不直接复用 |

## 三、从老系统提炼出的可迁移逻辑

### 1. 稳定模式逻辑

老系统提出：系统健康后，自愈检测应进入稳定模式，避免持续干预用户操作。

迁移到新系统后，含义是：

- 开机自检通过后，后台守护应降噪。
- 健康状态明确时，不重复重启或反复修复。
- 稳定不是守护越多越好，而是该安静时安静。

### 2. 根因下探逻辑

老系统的经验是：反复故障不能在同一层反复补丁。

迁移规则：

- 首次故障按标准排查。
- 反复故障必须逐层下探。
- 两层内找不到根因，继续向组件内部机制、服务注册、端口占用、持久化路径和调度机制追查。

### 3. 适配机制而非对抗机制

Ollama 模型目录问题说明：组件有自己的内部行为，系统不应盲目对抗，而应理解并适配。

迁移规则：

- 先看组件实际怎么运行，再决定修复。
- 先观察日志和真实目录，再改脚本。
- 自动化必须顺应组件机制，而不是靠外部强压。

### 4. 服务注册与端口治理逻辑

幽灵服务案例说明：只 kill 进程不 disable 服务，会让旧服务重启后复活。

迁移规则：

- 自建服务必须登记。
- 废弃服务必须停用、禁用、删除服务文件并验证。
- 新端口必须先查端口表和现役入口。
- 端口冲突先查进程来源和服务注册，不只看当前 PID。

### 5. 感知-记忆-决策-行动闭环

老系统已有雏形模块：

- 感知：采集 CPU、内存、磁盘、Docker、Ollama。
- 记忆：记录事件、状态和决策。
- 决策：按阈值和规则生成动作建议。
- 行动：执行备份、清理、重启等动作。

迁移到新系统后，必须加上新的安全闸口：

```text
感知 -> 记忆 -> 决策建议 -> 边界审查 -> 人工/授权闸口 -> 行动 -> 回执 -> 进化
```

旧系统的“行动模块”不能原样进入新系统正式链路；新系统必须先保留只读、模拟、回执和授权边界。

### 6. 双通道协作逻辑

股票系统旧方案提出被动响应和主动推送双通道。

迁移规则：

- 被动响应适合用户查询和明确命令。
- 主动推送适合已验证的提醒、日报、异常告警。
- 主动通道必须比被动通道更严格，尤其企业微信真实发送、n8n触发、交易、税务、视频发布都必须保持闸口。

### 7. 旧系统反面教训逻辑

老系统暴露过服务名漂移、端口漂移、版本漂移、配置漂移、旧服务复活、固定等待误判等问题。

迁移规则：

- 旧方案只能作依据之一，不作最高依据。
- 新系统以当前总管面板、最新接续包、现役端口、当前验收和正式边界为准。
- 任何旧资产进入新系统前，必须标明“通用、专有、不适配、替代方案”。

## 四、旧资产吸收强制八问

任何来自 F 盘老系统资产的材料，进入新系统前必须回答：

1. 它是原则、经验、模板、代码、工作流、日志、数据还是密钥线索？
2. 它在老系统中是否经过真实验证？
3. 它解决的是根因问题，还是只是当时的补丁？
4. 它是否依赖旧目录、旧端口、旧服务名、旧模型版本或旧工作流？
5. 它是否可能触发真实发送、n8n、正式库写入、重启服务、交易、税务办理或视频发布？
6. 它能否先以只读、影子、模拟或回执形式验证？
7. 它应沉淀为规则、模板、验收项、故障卡，还是只留索引？
8. 它有哪些不适配当前新系统的地方？

## 五、禁止事项

- 禁止直接把旧系统脚本覆盖到新系统正式脚本。
- 禁止直接恢复旧 n8n 工作流为启用状态。
- 禁止读取、复制、外传或扩散密钥线索。
- 禁止用旧端口、旧服务名、旧路径覆盖当前总管登记。
- 禁止把旧股票主动推送逻辑直接变成当前真实外发。
- 禁止把旧自动清理、重启、删除类动作接入无人值守正式执行。
- 禁止把旧系统“曾经能跑”当作当前可交付证据。

## 六、可进入当前系统的优先资产

1. 稳定模式和守护降噪思想。
2. 根因下探排障方法。
3. 服务注册、端口表、废弃服务彻底禁用规则。
4. 感知-记忆-决策-行动闭环，但行动前新增边界审查。
5. 双通道协作的职责分离思想。
6. 脚本标头、变更留痕、回退路径、验收三维审视。
7. 旧问题 ADR 化、规则化、验收化。

## 七、验收口径

旧系统资产吸收完成，不看搬了多少文件，而看是否做到：

- 旧经验已被分类。
- 旧风险已被隔离。
- 旧机制已被反适配。
- 新系统没有继承旧混乱。
- 可用经验已进入规则、验收或故障卡。
- 不可用资产只留索引和边界说明。

## 八、总则

旧系统不是包袱，也不是捷径。

它的价值在于告诉新系统哪些路走通过、哪些坑踩过、哪些机制值得保留、哪些旧习惯必须切断。吸收旧系统，就是把历史变成判断力，而不是把历史原样搬回来。
