# 同日修复后复核入账规则 v1.0

## 一、规则目的

解决“发现问题”和“解决问题”之间的入账判断过粗问题。

系统不能把所有失败都机械推迟到下一自然日，也不能因为后来修好了就抹掉原始失败。正确做法是：

1. 原始失败如实记录。
2. 问题性质分型。
3. 修复动作可追溯。
4. 复验覆盖原失败项。
5. 再判断是否允许同日修复后复核入账。

## 二、适用范围

适用于正式稳定交付样本采集期间的 P1 级问题，尤其是：

- 局部职责分流缺口。
- 局部入口路由缺口。
- 巡检口径偏差。
- 小范围配置或脚本逻辑缺陷。

不适用于：

- 红线命中。
- 真实外发、n8n 正式触发、正式库写入。
- 交易、税务办理、视频发布。
- 核心依赖持续不可用。
- 需要大范围重构或无法证明边界的问题。

## 三、判断链

同日修复后复核不得只看“最后是否通过”，必须按以下顺序判断：

1. 原始样本是否真实发生。
2. 原始失败是否完整记录。
3. 失败是否有明确根因。
4. 问题是否为 P1-B 或 P1-C。
5. 修复是否小范围、可追溯、可回滚。
6. 复验是否覆盖原失败项。
7. 总回归是否通过。
8. 红线是否为 0。
9. 是否只形成一个当日候选样本。
10. 是否保留原始失败和修复后复核两个证据层。

## 四、输出要求

如果允许同日修复后复核入账，必须生成独立回执，写清：

- 原始失败回执路径。
- 修复回执路径。
- P1 子类。
- 入账依据。
- 复验结果。
- 红线扫描结果。
- 样本日期。
- 结论是“同日修复后复核入账”，不是覆盖原始失败。

## 五、对系统能力的要求

这条规则要求系统处理问题时更细：

- 不机械照搬旧规则。
- 不用“保守”或“激进”替代判断。
- 先拆问题，再看证据。
- 既保留历史真实，又承认修复后的真实。
- 让规则服务于解决问题，而不是让规则遮蔽问题。
