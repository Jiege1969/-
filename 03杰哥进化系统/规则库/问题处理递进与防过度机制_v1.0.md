# 问题处理递进与防过度机制

> 版本：v1.0  
> 生效日期：2026-05-09  
> 所属系统：03杰哥进化系统 / 规则库  
> 定位：规定系统发现问题后的递进处理链条，确保问题处理落脚点是解决问题，同时能从源头治理、举一反三，并防止过度防范变成新的复杂度

## 一、核心原则

发现问题后，系统不能只停留在记录，也不能直接跳到大范围加规则。

正确顺序是：

```text
如实记录 -> 找到原因 -> 分析成因 -> 制定解决办法 -> 落地解决 -> 总结疏漏 -> 源头治理 -> 举一反三 -> 建立防范机制 -> 防止过度防范
```

这是一条层层递进的链，不是并列清单。

## 二、每一层的职责

| 层级 | 目标 | 输出 |
|:---|:---|:---|
| 如实记录 | 不美化、不掩盖、不伪造通过 | 原始事实、时间、来源、失败项 |
| 找到原因 | 区分现象和原因 | 直接原因 |
| 分析成因 | 追问为什么会发生 | 根因、触发条件、依赖关系 |
| 制定办法 | 明确如何解决 | 修复方案、边界、风险 |
| 落地解决 | 真正消除当前问题 | 修复结果、复验记录 |
| 总结疏漏 | 找出流程、规则、验收缺口 | 疏漏清单 |
| 源头治理 | 防止同源问题重复发生 | 规则、检查项、模板或脚本改进建议 |
| 举一反三 | 识别同类场景 | 同类风险清单 |
| 建立防范 | 加入合理护栏 | 验收项、闸口、巡检或提醒 |
| 防止过度 | 避免把低概率问题放大成系统负担 | 克制边界、观察期、暂不施工项 |

## 三、递进规则

1. 没有事实记录，不进入根因分析。
2. 没有根因判断，不急于新增规则。
3. 没有解决当前问题，不把总结当完成。
4. 没有复验结果，不宣布修复。
5. 没有重复性或迁移价值，不升级为全系统规则。
6. 没有明确收益，不新增复杂防范机制。

## 四、问题分流

| 类型 | 处理 |
|:---|:---|
| 一次性偶发 | 记录、复验、观察，不立即扩张规则 |
| 口径不一致 | 对齐上位原则和当前正式口径，修正文档或验收项 |
| 真实功能失败 | 修复功能并复验，不只写说明 |
| 红线命中 | 立即暂停，人工确认，进入 P0 |
| 同类重复出现 | 进入源头治理和防范机制 |
| 低概率想象风险 | 记录为观察项，不进入施工 |

## 五、举一反三的边界

举一反三不是无限联想。

只有满足以下条件之一，才进入防范机制：

- 同类问题已出现 2 次以上。
- 问题一旦发生会触碰红线。
- 问题会影响用户真实使用。
- 问题暴露出上位规则缺口。
- 低成本检查能显著降低复发概率。

不满足条件的，先进入观察或待讨论，不新增脚本、流程或闸口。

## 六、防过度机制

防范机制也要受治理。

新增防范前必须回答：

1. 这个问题是否已经解决？
2. 这个问题是否有复发风险？
3. 复发后影响多大？
4. 防范成本是否小于复发成本？
5. 现有规则是否已经覆盖？
6. 能否用轻量提醒、验收项或模板解决，而不是新增复杂脚本？
7. 是否会拖慢主线交付或制造误伤？

如果答案不清楚，先不施工，只记录观察项。

## 七、与稳定交付的关系

正式稳定验证期间，任何失败都必须按本机制处理：

- 当天样本如实记录。
- 不把失败日伪装成通过日。
- 先定位失败项，再判断红线或 P1/P2/P3。
- 当前问题未解决前，不用哲学总结替代修复。
- 修复后必须复验。
- 若能证明是同类缺陷，再进入源头治理和举一反三。

## 八、总则

问题处理的落脚点是解决问题。

总结归纳是为了更好地解决问题，源头治理是为了少重复解决同类问题，举一反三是为了让系统更聪明。但防范不能过头，不能把每个可能性都变成规则、脚本和闸口。

同时，解决问题必须防止方向性错误。埋头拉车负责脚踏实地修当前问题，抬头看路负责确认修复方向仍然正确。若方向错了，越努力越容易把系统推向更深偏差；这时应先做方向校准，再继续施工。

真正成熟的系统，既不遮掩问题，也不被问题吓住；既能修眼前，也能治源头；既会举一反三，也知道适可而止。
