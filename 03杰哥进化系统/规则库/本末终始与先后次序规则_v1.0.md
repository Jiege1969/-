# 本末终始与先后次序规则

> 版本：v1.0  
> 生效日期：2026-05-08  
> 所属系统：03杰哥进化系统 / 规则库  
> 定位：规定哲学思想、方法论、系统规则、施工动作、验收回执之间的先后顺序，防止系统把上位原则、下位方法和具体动作平铺混用

## 一、核心出处

```text
物有本末，事有终始。知所先后，则近道矣。
```

在杰哥智能化系统中，这句话的含义是：

- 任何系统都有本和末。
- 任何事情都有开始和结束。
- 任何施工都有先后和依赖。
- 知道什么在前、什么在后，系统才接近正确的运行之道。

## 二、系统中的本末

| 层级 | 本末定位 | 说明 |
|:---|:---|:---|
| 系统总目标 | 本 | 为什么搭建这个系统，服务什么真实使用 |
| 哲学思想 | 本 | 系统如何理解稳定、边界、智能、进化 |
| 方法论 | 中 | 把思想转成可执行方法 |
| 规则与模板 | 中 | 把方法固化为检查、边界和复用资产 |
| 脚本与工作流 | 末 | 具体执行动作 |
| 文件与回执 | 末 | 执行结果和证据 |

末不是不重要，但末必须服从本。脚本、文件、回执不能反过来定义系统总目标。

## 三、系统中的终始

任何系统动作都必须有清楚的开始和结束。

开始不是“想到一个点子”，而是完成方向校准、边界确认和依赖检查。

结束不是“生成一个文件”，而是完成验收、回执、接续和必要的进化沉淀。

标准链路：

```text
目标确认 -> 本末判断 -> 先后排序 -> 依赖检查 -> 影子/只读验证 -> 执行动作 -> 验收回执 -> 复盘提炼 -> 进化沉淀
```

## 四、哲学方法论的先后顺序

系统中的思想和方法也有启动顺序：

1. 先问总目标：这件事服务什么真实使用？
2. 再问本末：这是根本原则、方法规则，还是具体动作？
3. 再问边界：能做什么，不能做什么？
4. 再问依赖：前置条件是否成立？
5. 再问路径：先影子、只读、样本，还是可以进入正式候选？
6. 再问验收：什么算完成？
7. 再问进化：哪些经验值得沉淀，哪些只是过程噪声？

## 五、与开机自检的对应关系

开机自检不能按固定时间机械等待，而要按依赖拓扑判断。

哲学方法论也一样，不能把所有原则同时启动，而要按层级和依赖启动：

```text
总目标未明 -> 不进入施工
边界未明 -> 不进入执行
前置未过 -> 后置跳过
影子未验 -> 不进正式
验收未过 -> 不称完成
复盘未做 -> 不称进化
```

## 六、先后错乱的典型风险

| 错乱类型 | 风险 |
|:---|:---|
| 以末代本 | 用脚本跑通、文件存在替代用户真实可用 |
| 未始先行 | 未确认边界就施工，造成越权或污染正式链路 |
| 未终称成 | 没有验收和回执就宣布完成 |
| 下位反压上位 | 旧脚本、旧口径、旧端口反过来覆盖总管规则 |
| 方法未验即升格 | 偶然有效的方法未经复验就变成系统原则 |
| 哲学停在文字 | 思想没有落成规则、验收或调度动作 |

## 七、施工强制七问

每次新增能力、吸收思想、复用旧资产、修复问题前，先问：

1. 这件事的本是什么，末是什么？
2. 它服务哪个系统总目标？
3. 它属于哲学、方法、规则、脚本、回执还是经验？
4. 它的前置条件是什么？
5. 哪些后续动作必须等它通过后才能继续？
6. 它怎样结束，验收证据是什么？
7. 它是否值得进入进化系统，还是只留过程记录？

## 八、验收口径

本规则是否生效，不看是否引用了这句话，而看后续施工是否做到：

- 先分本末，再排任务。
- 先定边界，再动执行。
- 先过前置，再启后置。
- 先做影子，再入正式。
- 先验收回执，再宣布完成。
- 先复盘筛选，再沉淀进化。

## 九、总则

系统稳定和系统智能，首先来自正确的先后顺序。

知道什么是本，什么是末；知道什么是开始，什么是结束；知道什么必须先做，什么必须等待，系统才不会乱忙、乱修、乱扩张，也才真正接近“道”。
