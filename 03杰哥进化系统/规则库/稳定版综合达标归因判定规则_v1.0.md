# 稳定版综合达标归因判定规则

> 版本：v1.0  
> 生效日期：2026-05-09  
> 所属系统：03杰哥进化系统 / 规则库  
> 定位：把正式稳定交付版从“单一三自然日口径”升级为“多证据综合归因判断”，在大原则下具体问题具体分析，避免机械等待，也避免降低标准。

## 一、根本原则

稳定版达标不是一个单项条件，而是一组证据共同指向同一结论。

```text
稳定达标
= 冷启动自恢复
+ 依赖顺序正确
+ 日常总回归通过
+ 业务入口巡检通过
+ 红线持续关闭
+ 问题可归因、可修复、可复验
+ 样本具备代表性
+ 用户可感知结果成立
```

三自然日样本是“跨日稳定性证据”，不是最高原则本身。冷启动重启验证是“系统自恢复能力证据”，也不是唯一证据。二者都服务于同一个上位目标：证明系统在真实状态变化下仍能稳定恢复、正确判断、守住边界、产生可追溯结果。

## 二、证据类型

| 证据 | 证明什么 | 局限 |
|:---|:---|:---|
| 三自然日样本 | 跨日状态、缓存、日志、日期边界、计划任务不只偶然通过 | 可能变成机械等时间，样本数量仍少 |
| 冷启动/重启验证 | 开机顺序、依赖恢复、自检链、服务可用、自恢复能力 | 单次重启不能证明长期稳定 |
| 日常总回归 | 业务入口、巡检、门禁、影子链路当前通过 | 只代表当前回归覆盖面 |
| 红线扫描 | 未外发、未触发 n8n、未交易、未办税、未发布 | 只证明边界关闭，不证明业务质量完整 |
| 问题分型复核 | 系统能记录、归因、修复、复验、回流经验 | 依赖证据完整性 |
| 用户可感知验证 | 用户实际能理解、使用、接续 | 需要真实使用反馈积累 |

## 三、综合判定状态

稳定版综合归因判定只允许输出以下状态：

| 状态 | 含义 |
|:---|:---|
| `stable_candidate_integrated_preconditions_passed` | 稳定版综合前置条件已通过，非机械等待，只差尚未执行的关键客观证据 |
| `ready_for_cold_restart_decisive_check` | 已具备通过冷启动重启验证补强稳定证据的条件 |
| `formal_stable_ready_by_composite_evidence` | 冷启动、回归、红线、归因、样本代表性均成立，可提交正式稳定达标建议 |
| `formal_stable_pending_cross_day_or_equivalent_evidence` | 主要链路通过，但仍缺跨日或等价客观证据 |
| `blocked_by_specific_cause` | 被明确原因阻断，必须先修复 |
| `needs_evidence` | 证据不足，不能判断 |

## 四、冷启动重启能否作为关键证据

可以，但必须满足前提。

一次重启不是为了“重启了就算”，而是为了验证以下客观事实：

1. 开机后依赖顺序正确，前置未通过时后置不硬跑。
2. Docker、Ollama、Redis、n8n、19300、19302、19310 等关键服务按依赖恢复。
3. 开机施工准备自检 `ready_for_codex=true` 且 warnings 为空。
4. 日常可用交付版一键只读总回归通过。
5. 企业微信、股票、视频、税收暂停边界、知识库等入口只读检查通过。
6. 红线仍关闭：不外发、不触发 n8n、不写正式库、不交易、不办税、不发布视频。
7. 出现失败时能进入问题分型，而不是机械判死或机械放行。

若这些全部成立，冷启动重启验证可以作为稳定版综合达标的关键客观依据之一。

## 五、三自然日与冷启动的关系

三自然日和冷启动不是互相否定，而是互相补强：

- 三自然日证明“跨日不偶然”。
- 冷启动证明“系统能自恢复”。
- 问题分型证明“失败能被正确处理”。
- 红线证明“能力扩展没有越权”。

若三自然日尚缺 1 个，但冷启动验证、回归、红线、归因、样本代表性全部成立，可以进入“综合达标建议候选”，并在建议书中明确：三自然日默认证据尚未完整，但已有冷启动等价补强证据；是否签收为正式稳定版，由总管按用户确认口径裁决。

## 六、禁止事项

- 不得把三自然日当成唯一真理。
- 不得把冷启动当成万能替代。
- 不得为了加速降低标准。
- 不得用单次通过掩盖长期样本不足。
- 不得用“严谨”包装机械等待。
- 不得用“灵活”包装证据不足。
